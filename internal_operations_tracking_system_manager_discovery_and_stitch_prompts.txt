INTERNAL OPERATIONS TRACKING SYSTEM
ROLE, KPI, LEAD, ROYALTY & UI-DESIGN DISCOVERY DOCUMENT
============================================================

PURPOSE
-------
This document consolidates the current system direction and converts the known
requirements into a practical discovery questionnaire for the Manager.

The immediate objective is NOT to invent final KPIs, lead rules, royalty
calculations, or approval policies. The purpose is to identify exactly what
the real business does so the Internal Operations Tracking System can be
designed around the firm's actual workflow.

The system should ultimately answer:

1. Who is the user?
2. What is the user's designation and operational responsibility?
3. What information may the user see?
4. What actions may the user perform?
5. What work is assigned?
6. How is that work measured?
7. How does a lead move through the business?
8. How does a lead generate royalty for the firm?
9. What decisions are made by each management level?
10. What information should management and the Chairman see?
11. What events must be recorded for audit and accountability?
12. What analytical information should the system derive from operational data?

============================================================
A. CURRENT SYSTEM MODEL
============================================================

SYSTEM NAME
------------
Internal Operations Tracking System

ARCHITECTURAL LAYERS
--------------------
Layer 1: Authentication & Authorization Layer

Layer 2: Management Layer

Layer 3: Intelligence & Analytical Layer


1. AUTHENTICATION & AUTHORIZATION LAYER
--------------------------------------
The login page is common to every user.

There is NO public registration page.

User accounts are manually created inside the system by an authorized
administrative user.

Typical provisioning sequence:

Authorized administrator
    -> create internal user account
    -> assign designation
    -> assign organizational information
    -> assign system role
    -> assign access level
    -> configure permitted scope/actions
    -> activate account
    -> record administrative action in audit history

Login sequence:

User opens system
    -> enters credentials
    -> validate credentials
    -> validate location/session context
    -> record login/session event
    -> resolve effective role and permissions
    -> route to appropriate dashboard

The user should not select "Chairman / Manager / Employee" on the login page.

If a person has more than one authorized role, the system may provide a
controlled role/workspace context switch after authentication.


2. MANAGEMENT LAYER
-------------------
The Management Layer contains the user-facing operational workspaces.

Current system roles:

1. Chairman
2. Senior Manager
3. General Manager
4. Lead Manager
5. Executive
6. IT System Analyst
7. Business Development Executive (BDE)
8. Social Media Manager
9. Graphic Designer
10. Admin
11. Super Admin

IMPORTANT ORGANIZATIONAL INTERPRETATION
---------------------------------------
For the current business model, treat the following as the main operational
employee categories unless the Manager confirms otherwise:

- Business Development Executive
- Social Media Manager
- Graphic Designer
- IT System Analyst, where applicable as an operational employee/technical
  specialist

The management structure is being represented more granularly in the system:

General Manager (main management role)
    -> Senior Manager
    -> Lead Manager
    -> Executive
    -> General Manager

These should be treated as distinct system roles for access and responsibility
purposes, while the General Manager remains the primary higher-level
management role in the current conceptual model.

Chairman is the highest business oversight role.

Admin and Super Admin are administrative system roles, not ordinary
operational employee roles.

The IT System Analyst may require elevated technical privileges but should
not automatically receive unrestricted business authority merely because the
role is technically privileged.


3. INTELLIGENCE & ANALYTICAL LAYER
---------------------------------
This layer receives operational data from the Management Layer and converts
it into:

- performance analytics
- task analytics
- workload analytics
- attendance/workforce analytics
- lead/pipeline analytics
- royalty/revenue-related analytics
- trend and pattern analysis
- exception/risk analysis
- predictive insights where actually supported
- automated reporting
- management insights

IMPORTANT:
Charts must not be decorative. Every analytical widget should answer a
business question.

B. CURRENT CORE WORK MODEL
============================================================

TASK MANAGEMENT
---------------
The current manager-side task workflow is conceptually:

Create task
    -> define deliverables
    -> set priority
    -> set due date / SLA
    -> assess employee bandwidth
    -> assign employee
    -> notify employee
    -> monitor execution
    -> handle blockers / overdue conditions
    -> receive submission
    -> review / QA
    -> approve OR request changes
    -> complete and close
    -> record audit history

Task reporting states:

- Assigned
- Pending
- Overdue
- Reassigned
- Completed

Operational execution states may include:

- In Progress
- Blocked
- Waiting for Review
- Approval / Review
- Issue Resolved
- Done / Closed

REASSIGNED is a transition/event, not a terminal state.

OVERDUE is an exception condition. It should lead to manager review/intervention
rather than simply meaning "continue working."


EMPLOYEE TASK EXECUTION
-----------------------
Employee task execution includes:

- acknowledge task
- start work
- update progress
- record work activity
- upload evidence
- raise blocker/issue
- receive manager intervention
- continue work
- submit completed work
- receive review result
- correct work if changes are requested
- resubmit
- reach final approval and closure


RECORD WORK ACTIVITY
--------------------
Record Work Activity is the history of what the employee did while executing
the task. It is not another task status.

It contains:

1. Progressive Update
   - current progress
   - work completed since the previous update
   - work remaining
   - timestamp

2. Work Notes
   - explanation of actions taken
   - observations
   - dependencies
   - problems encountered
   - decisions/context
   - resolution notes

3. Time-Spent / Effort Entry
   - task-level effort
   - duration or hours
   - activity category where required
   - timestamp
   - correction/change history

4. Supporting Documents / Evidence
   - work artifacts
   - reports
   - screenshots
   - test results
   - drafts
   - deliverables
   - other supporting files

Audit should distinguish:
- state changes
- work-activity records
- administrative changes
- review/approval events
- file/version changes
- reassignment events

============================================================
C. LEAD-CENTRIC BUSINESS MODEL
============================================================

The firm works on LEADS and the firm's ROYALTY is connected to leads.

This makes Lead Management and Royalty Tracking important additions to the
system.

DO NOT assume the royalty formula until the Manager confirms it.

The system should be capable of representing:

Lead acquisition
    -> lead qualification
    -> lead ownership/assignment
    -> lead follow-up/activity
    -> lead status progression
    -> conversion / business event
    -> royalty-eligible event
    -> royalty calculation/record
    -> management reporting
    -> Chairman-level royalty visibility

The exact meaning of "converted", "successful lead", "royalty-eligible lead",
"royalty earned", timing of recognition, and ownership attribution must be
confirmed with the Manager.

L. DESIGN PRINCIPLE TO KEEP THROUGHOUT THE PROJECT
============================================================

The system should connect BUSINESS ACTIVITY to MANAGEMENT INSIGHT.

For lead-driven operations, the central chain is:

Lead
    -> Assigned Employee
    -> Activity
    -> Qualification
    -> Follow-up
    -> Conversion
    -> Royalty
    -> Analytics
    -> Management Insight
    -> Decision / Action
    -> Audit

For task-driven operations:

Task
    -> Assignment
    -> Execution
    -> Work Activity
    -> Blocker / Overdue
    -> Manager Intervention
    -> Submission
    -> Review
    -> Correction / Approval
    -> Completion
    -> Analytics
    -> Audit

The system should therefore be designed as an operational tracking and
decision-support platform, not merely as a collection of CRUD screens.
