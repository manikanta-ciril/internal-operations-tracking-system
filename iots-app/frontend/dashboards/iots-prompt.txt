*CIRIL - Internal Operations Tracking System*
*STITCH PROMPT:1*
Design a complete enterprise-grade internal web application called:

INTERNAL OPERATIONS TRACKING SYSTEM

This is an internal organizational operations platform, NOT a public SaaS product, NOT a marketing website, and NOT a generic employee management template.

The product is used by an organization to securely authenticate users, control access, manage operational work, execute tasks, monitor attendance and availability, handle requests and escalations, maintain traceable work history, and transform operational data into management intelligence and analytical insights.

The system is organized conceptually into three major layers:

1. AUTHENTICATION & AUTHORIZATION LAYER
2. MANAGEMENT LAYER
3. INTELLIGENCE & ANALYTICAL LAYER

==================================================
1. AUTHENTICATION & AUTHORIZATION
==================================================

There is NO public registration page.

All user accounts are created manually inside the system by authorized administrative users.

The account creation process creates an internal user profile and associates:
- employee identity
- designation
- organizational location
- team/department where applicable
- access level
- system role
- account status
- permitted permissions

The login screen is COMMON to every user.

Do NOT create separate login pages for Chairman, Manager, Employee, Admin, etc.

The login process visually represents:

User opens system
→ enters credentials
→ credentials are validated
→ location/session context is validated
→ login activity is recorded
→ system determines effective role and permissions
→ user is routed to the appropriate role-specific dashboard

Do NOT ask the user to choose their role on the login page.

The system determines role and authorization from the user's account configuration.

If a user has multiple authorized roles/designations, provide a subtle post-login workspace/role context switcher rather than putting role selection on the login page.

Unknown or unusual login locations should be represented as an operational security condition, not as a frightening error screen.

==================================================
2. ACCESS MODEL
==================================================

Use two broad access bands:

HIGHER-LEVEL ACCESS
LIMITED ACCESS

However, do not visually imply that Limited Access means "unimportant".

Actual authority depends on:
- role
- data scope
- permitted actions
- organizational responsibility
- authorization rules

Use role-based access control concepts.

The interface should hide or disable controls that the current role is not authorized to use.

==================================================
3. ORGANIZATIONAL ROLES
==================================================

Design role-specific interfaces for:

1. Chairman
2. Senior Manager
3. General Manager
4. Lead Manager
5. Executive
6. IT System Analyst
7. Business Development Executive
8. Social Media Manager
9. Graphic Designer
10. Admin
11. Super Admin

Do not make these eleven dashboards look like eleven unrelated products.

Use one consistent application shell and design system, while changing:
- navigation
- widgets
- metrics
- actions
- data visibility
- approval capabilities
- management capabilities
- technical controls

according to role.

==================================================
4. MANAGEMENT MODEL
==================================================

Management responsibilities are separated from employee execution.

Managers manage:
- tasks
- priorities
- deadlines
- employee workload
- team availability
- leave/roster
- performance
- blockers
- escalations
- quality review
- approvals
- operational targets

Employees execute assigned work, update progress, record work activity, submit work, and raise issues.

Administrative users manage organizational/system-level operations within their authorization scope.

Do not turn every role into an administrator.

==================================================
5. TASK LIFECYCLE
==================================================

Tasks follow a controlled operational lifecycle.

Core reporting states include:

ASSIGNED
PENDING
OVERDUE
REASSIGNED
COMPLETED

Do not treat REASSIGNED as a final state.

Task execution may contain operational micro-states such as:
- In Progress
- Blocked
- Waiting for Review
- Approval / Review
- Issue Resolved
- Done / Closed

The interface must distinguish:
- task status
- task execution state
- work activity
- review outcome
- audit history

==================================================
6. EMPLOYEE WORK EXECUTION
==================================================

Employee task execution should support:

- task acknowledgement
- starting work
- progress updates
- work notes
- time/effort entries
- supporting documents/evidence
- blocker reporting
- issue tickets
- manager intervention
- escalation when unresolved
- submission for review
- correction cycle
- resubmission
- final approval
- closure

Manager rejection must not simply terminate the task.

If changes are requested:
Manager feedback
→ Employee returns to task execution
→ Work is corrected
→ Work is resubmitted
→ Manager reviews again

==================================================
7. OVERDUE LOGIC
==================================================

Overdue is an exception state.

Do NOT make:

Overdue
→ Continue Working

the only path.

Instead visually support:

Overdue
→ Manager reviews overdue task
→ Manager intervention / resolution
→ Continue / extend deadline / reassign / escalate
→ Task returns to the operational workflow

Use appropriate warning/attention states without making the interface visually alarming.

==================================================
8. RECORD WORK ACTIVITY
==================================================

The employee can record:

Progress Update
Work Notes
Time-Spent / Effort Entry
Supporting Documents / Evidence

These are activity records, not independent task statuses.

The system should visually show that multiple work-activity records can exist during the same task state.

Activity history should be chronological.

==================================================
9. AUDITABILITY
==================================================

Important operational actions should be traceable.

Provide a reusable audit/history component capable of showing:

- actor
- timestamp
- action
- previous value
- new value
- reason/comment where applicable
- related task/user/request
- system-generated vs user-generated event

Audit history is primarily presented as read-only evidence.

Do not make audit logs look like ordinary editable data tables.

==================================================
10. INTELLIGENCE & ANALYTICAL LAYER
==================================================

The third layer is called exactly:

INTELLIGENCE & ANALYTICAL LAYER

It analyzes operational information generated by the system.

It may provide:

- performance analytics
- task analytics
- workload analytics
- attendance/workforce analytics
- trend and pattern analysis
- exception and risk analysis
- predictive insights where supported
- automated reports
- management insights

Do not turn this into meaningless decorative charts.

Every chart should answer a business question.

Examples:
- Are tasks being completed on time?
- Where are bottlenecks?
- Is workload uneven?
- Which work is repeatedly overdue?
- Which tasks are repeatedly reassigned?
- How is team performance changing?
- Which issues require management attention?

==================================================
11. COMMON ENTERPRISE UI SHELL
==================================================

Create a consistent desktop-first enterprise workspace.

Use:

- left navigation sidebar
- compact global header
- organization/system identity
- current user and role
- current branch/location
- availability indicator
- global notifications
- global search
- breadcrumbs
- contextual actions
- responsive content grid

Recommended layout:
- 12-column desktop grid
- desktop-first design around 1440px
- responsive tablet/mobile adaptation
- consistent spacing system
- accessible typography
- strong visual hierarchy
- dense but readable information presentation

Use a professional enterprise visual language:
- restrained
- precise
- modern
- data-oriented
- trustworthy
- calm
- operational

Avoid:
- marketing-style hero sections
- huge decorative illustrations
- excessive gradients
- excessive glassmorphism
- oversized empty cards
- childish dashboard widgets
- unnecessary 3D charts
- excessive rounded containers
- visually noisy neon aesthetics

Use Material/enterprise UI principles as a foundation but create a distinctive internal-operations identity rather than making the product look like a Google clone.

Use semantic status indicators consistently for:
- normal
- pending
- warning
- overdue
- blocked
- success
- critical

Ensure status meaning is not conveyed by color alone.

==================================================
12. DATA-DENSE BUT EXECUTIVE-FRIENDLY
==================================================

The product must satisfy two audiences:

Senior management needs fast understanding.

Operational users need detailed controls.

Therefore:
- executives receive high-level summaries first
- managers receive actionable operational detail
- employees receive task-focused execution tools
- administrators receive controlled configuration tools
- technical roles receive diagnostics and system information

Use progressive disclosure.

Do not put every function on the first screen.

==================================================
13. INTERACTION DESIGN
==================================================

Use:
- drawers for quick inspection
- modals for focused confirmations
- side panels for contextual details
- tabs for related information
- expandable audit history
- filterable tables
- saved views where useful
- clear empty states
- confirmation for destructive/high-impact actions
- inline validation
- toast notifications for completed actions
- persistent status visibility

Tables should support:
- search
- filters
- sorting
- pagination
- column visibility
- export where authorized

==================================================
14. IMPORTANT UX PRINCIPLE
==================================================

The design should look "complex underneath, simple on top."

A Chairman should understand the dashboard within seconds.

A Manager should be able to operate their team without opening ten screens.

An Employee should immediately know:
- what requires attention
- what task they are working on
- what is due
- what was requested from them
- what they need to submit

Create a cohesive enterprise product, not a collection of generic AI-generated dashboards.
