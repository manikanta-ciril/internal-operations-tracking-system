You are acting as a Senior Enterprise Systems Architect, Solution Architect,
Business Process Architect, Security Architect, Data Architect, and UI/UX
Systems Architect.

You are designing the complete enterprise architecture of:

CIRIL
Internal Operations Tracking System (IOTS)

Organization:
Commercial Real Estate Institutional Alliance (CIRIL)

System Purpose:
Design one coherent internal enterprise platform that connects authentication,
authorization, employee operations, managerial control, commercial operations,
task execution, attendance, geolocation, security auditing, analytics,
reporting, performance measurement, and management intelligence.

IMPORTANT:
This is NOT a generic CRM.
This is NOT a generic HRMS.
This is NOT simply a dashboard collection.
This is an internal operations-control platform designed specifically around
CIRIL's business and organizational workflow.

The architecture must therefore represent BOTH:

1. What the organization does
2. How the software enables, controls, records, and analyzes what the organization does

========================================================
1. PRIMARY ARCHITECTURAL PRINCIPLE
========================================================

Use the following principle throughout the architecture:

"COMPLEX UNDERNEATH, SIMPLE ON TOP."

The underlying system must support:
- detailed permissions
- multiple organizational roles
- workflow/state transitions
- task history
- work activity history
- geolocation records
- attendance records
- financial/royalty records
- document versions
- audit history
- analytics
- exception detection
- automated reporting
- multi-role contexts

However, the visible user experience must remain:
- clean
- understandable
- calm
- professional
- enterprise-grade
- information-dense without becoming visually chaotic

Do not design the system as a collection of disconnected modules.

Show the dependencies and relationships between modules.

========================================================
2. ARCHITECTURAL FOUNDATION
========================================================

The business architecture MUST be organized into the following three
foundational layers:

LAYER 1
Authentication, Geolocation & Security Layer

LAYER 2
Management, Operations & Execution Layer

LAYER 3
Intelligence, Analytics & Reward Layer

Treat these three as the top-level conceptual architecture.

However, do not confuse these business layers with conventional software
layers.

Underneath the three conceptual layers, show the technical architecture
required to make them operate.

The technical architecture may include, where appropriate:

- Presentation / UI Layer
- Application / Domain Layer
- Workflow & Business Rules
- Authorization / Policy Enforcement
- Integration / API Services
- Background Processing
- Data Persistence
- File / Document Storage
- Analytics / Reporting
- Audit / Event Infrastructure
- Monitoring / Observability
- Security Infrastructure

Do NOT arbitrarily choose technologies merely to make the diagram look more
technical.

Where implementation technology has not been formally confirmed, label the
component by responsibility rather than inventing a technology.

4. LAYER 1 — AUTHENTICATION, GEOLOCATION & SECURITY
========================================================

Design Layer 1 as the secure entry and identity-control boundary.

The common login flow must be:

User
→ Credentials Submitted
→ Credential Validation
→ Location Verification
→ Session / Security Context Creation
→ Audit Recording
→ Role / Permission Resolution
→ Workspace Routing

There is:

- NO public self-registration
- ONE common corporate login
- internally provisioned accounts
- automatic role determination
- support for users with multiple authorized roles

The user MUST NOT select their job role manually during login.

The system determines the user's authorized role context.

--------------------------------------------------------

The architecture must distinguish the documented macro reporting states:

- ASSIGNED
- PENDING
- OVERDUE
- REASSIGNED
- COMPLETED

Important:

REASSIGNED is a transition/event, not a terminal state.

OVERDUE is an exception state requiring action.

COMPLETED is the terminal approved state.

--------------------------------------------------------

- In Progress
- Blocked
- Waiting for Review
- Under Review / QA
- Changes Requested
- Issue Resolved
- Done / Closed

Do not treat these as a flat list.

Represent them as a state machine with permitted transitions.

========================================================
12. WORK ACTIVITY ARCHITECTURE
========================================================

Keep TASK STATE and WORK ACTIVITY as separate concepts.

State answers:

"Where is the task in the workflow?"

Activity answers:

"What did the employee actually do?"

Structured Work Activity consists of:

1. Progress Update
2. Work Notes
3. Time / Effort Entry
4. Supporting Evidence / Deliverables

An employee may create multiple activities during one task state.

The architecture must therefore model:

Task
→ Task State History

and separately:

Task
→ Work Activity Stream

These streams may be displayed together in the UI but must remain
conceptually distinct.

========================================================
45. ARCHITECTURE QUALITY RULES
========================================================

The final architecture must:

1. Avoid spaghetti connections.
2. Avoid duplicate components.
3. Clearly distinguish domains.
4. Clearly distinguish users from system services.
5. Clearly distinguish business processes from technical infrastructure.
6. Show direction of information flow.
7. Show major decision points.
8. Show system boundaries.
9. Show trust/security boundaries where meaningful.
10. Show data ownership / responsibility.
11. Show which systems generate events.
12. Show which systems consume events.
13. Show which data is transactional.
14. Show which data is analytical.
15. Show where audit is written.
16. Show where authorization is enforced.
17. Show where workflow rules are enforced.
18. Show how exceptions return into the workflow.
19. Show how analytics feeds management.
20. Never make the architecture look more complex merely to appear technical.

========================================================
47. IMPORTANT: DO NOT INVENT MISSING BUSINESS RULES
========================================================

Where the provided CIRIL documentation defines a rule, preserve it.

Where the documentation does NOT define a rule:
- mark it as configurable
- mark it as pending business confirmation
- or explicitly identify it as an architectural recommendation

Do not silently invent:
- new roles
- new approval authorities
- financial rules
- employee policies
- legal policies
- exact infrastructure vendors
- exact databases
- exact cloud providers
- exact API providers
- exact security algorithms

The architecture must distinguish:

DOCUMENTED REQUIREMENT
vs.
ARCHITECTURAL RECOMMENDATION
vs.
IMPLEMENTATION DECISION

48. FINAL DESIGN OBJECTIVE
========================================================

The finished IOTS architecture should communicate three things simultaneously:

1. TO MANAGEMENT:
   "This system understands how CIRIL operates."

2. TO TECHNICAL PEOPLE:
   "This system has properly separated identity, authorization,
   workflow, data, integrations, audit, analytics, and infrastructure."

3. TO THE CHAIRMAN:
   "This system provides visibility, accountability, operational control,
   commercial visibility, and actionable intelligence from one connected
   platform."

The final result should look like an architecture of a real enterprise
operations platform — not a generic CRM diagram, not an organizational
chart, and not a collection of UI screens.
