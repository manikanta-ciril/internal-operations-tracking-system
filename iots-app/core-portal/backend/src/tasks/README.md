# Shared task and work records

Mounted at `/api/auth/tasks`, beneath the existing active session and attendance-photo guards. Commands re-read current role assignments inside the existing session transaction. GM/SM can allocate and manage firm work; the named independent reviewer decides a submission. Chairman has oversight. Lead Manager and Executive alone have no staff supervision rights. Capability decisions use the employee's complete role set, not the selected dashboard.

`GET /` returns authorised tasks, eligible directory, current user, permissions and reports. `POST /` saves a draft. `POST /:id/actions` applies a validated command with `revision`. Every write requires an `Idempotency-Key` (12–80 letters, digits, hyphens or underscores). Retrying the same key and payload returns its saved response; reusing it for another intent returns 409. Successful task changes, immutable event records and in-app notifications commit together. External email delivery is not configured.

Supported actions: edit, assign, start, note, progress, work-update, effort, block, resolve, resume, checklist, request-deadline, decide-deadline, save-draft, submit, review-start, approve, changes, reassign, delegate-reviewer, publication-proof and cancel. Progress remains separate from status. Effort is capped at 1440 minutes per employee/work date. Transfer retains earlier contributors with read-only access, assignments and authorship. Submission versions retain their selected file references; changing a working draft cannot alter an earlier submission. Original due date survives extensions. Optional publication-required work cannot close before evidence is recorded.

`POST /:id/files` accepts a raw binary body (30 MB maximum) and URL-encoded `X-File-Name`. A creating manager can upload draft references using `X-File-Purpose: reference`. Employees upload their own active task evidence. `POST /report-files` uploads personal report evidence. `GET /files/:id` checks current task/report access and forces downloads with a sandbox policy. Adding `?preview=1` permits only supported raster images, PDF, plain text, video and audio with their safe content types; SVG, HTML and opaque creative/office source formats cannot be previewed. Blob preview frames must also be sandboxed by the frontend. Storage is outside the public web root under `IOTS_TASK_ROOT` or `.local/task-evidence`, using generated keys. Root-relative `sendFile` keeps the generated key protected while allowing the private `.local` storage directory. Metadata contains SHA-256 and uploader. Supported documents, images, creative sources and audio/video have extension checks and signature validation where available; images use the existing decoder. Opaque source formats are never rendered inline, archives are never extracted. Antivirus scanning, comprehensive content inspection and retention automation remain deployment work, not capabilities claimed here.

`rate` accepts a whole-number `score` from 1 to 5 and a required explanatory `note` only after completion. The current named GM/SM reviewer must be different from the owner. One immutable rating stores the actor, time and reviewed version, increments the revision and appends an audited event. Chairman accounts cannot be assigned employee work even when another execution role is also present.

`POST /reports` accepts `{report,revision,submit}`. Report date and task contribution scope are validated; referenced evidence must be saved and authored by the employee. Server records task facts and current GM/SM recipients. Submitted reports are immutable. Report content and files are available to managers/Chairman only after submission; drafts remain private.

The additive MySQL migration is `npm run migrate:tasks` with the application's existing DB environment. It creates task snapshots with indexed ownership/state/deadline columns, append-only event records, command receipts, private-file metadata and daily reports. It does not seed tasks or alter accounts. Task updates lock individual rows; employee/session locking serializes same-account changes and duplicate commands. JSON task snapshots preserve the existing UI contract; further relational normalization and pagination should follow measured need.

Verification: `npm run test:tasks` runs an isolated disposable MySQL database and private temporary upload directory; `npm run test:unit` and `npm run test:auth` cover existing behavior. `node tests/task-browser-fixture.cjs` creates another isolated database and serves the actual built frontend on port 5198 with test-only session credentials printed as a temporary JSON-file path. These sessions and synthetic attendance never touch the live database. Do not use that fixture as an application launch command or expose it publicly.
